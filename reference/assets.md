# 做素材：从设计稿/实拍照片到图集

这一篇讲**怎么把一张参考图变成工程能用的图集**，以及做的过程中会翻车的地方。
格式怎么选（RGB565 / ARGB8565 / JPEG）、假透明、棋盘格自检在 `platform.md` 第 4 节。

> 本篇大部分内容来自一次"照着实拍照片重做整页界面"的实战（改了七八轮），
> 数字都是那次实测的。换个字体/屏幕，方法一样，数字要自己重新量。

---

## 1. ⚠ 字号不能按画布高度设，要按目标墨迹高度反推

**最容易翻车的一条**，而且翻了车不容易想到原因：字形会一律偏小约 25%。

原因：字号包含上下的行间留白，**墨迹只占其中一部分**。
所以拿"画布高度"当字号，画出来的字必然缩水：

| | 参考图墨迹 | 按画布高设字号（错） | 按实测反推（对） |
|---|---|---|---|
| 大数字 `8` | 38×56 | **23×41** | 35×56 |
| 秒 `2` | 25×36 | 17×26 | 24×36 |

### ⚠ 不要用比例系数，要实测

墨迹占字号的比例**跨字体、跨字符都差很多**，没有能套用的常数
（实测 PIL 字号 100 下的墨迹高 / 字号）：

| 字体 | 数字 | 汉字 |
|---|---|---|
| Bahnschrift | 0.73 | 0.71 |
| 微软雅黑 Bold | 0.78 | **0.98** |
| Arial Bold | 0.73 | 0.63 |
| 宋体 | 0.68 | 0.92 |
| Calibri | 0.65 | 0.63 |

数字 0.65~0.78、汉字 0.63~0.98，而且**同一字体内跨字符也差很多**：
微软雅黑 Bold 的「度」0.98、「六」0.97，但 `℃` 只有 0.78、`-` 只有 0.12。

**正解是量一次再外推，对任何字体任何字符串都准**：

```python
def fit_font(text, ink_h, fpath, variation=None):
    """返回一个字号，使 text 的实际墨迹高度 ≈ ink_h。"""
    f = font(fpath, 100, variation)          # 基准字号量一次
    bb = ink_bbox(text, f)                   # 实际墨迹包围盒，不是 textbbox
    size = int(round(100 * ink_h / (bb[3] - bb[1])))
    # 线性外推后再 ±1 收敛一次，消掉取整误差
    ...
    return font(fpath, size, variation)
```

⚠ **量的必须是"实际墨迹包围盒"**（把字渲染到临时层上取非空像素的外接框），
不是 `textbbox()` —— 后者带着字体的行高信息，量出来偏大。

> 用比例系数还有个隐蔽的坏处：它和下面那个"临时层被裁"的坑会形成**正反馈** ——
> 比例法量偏小 → 把字号调大 → 更容易被临时层裁掉 → 量得更偏小。
> 实战里为此连踩两次。换成实测法一次收敛，比补一堆警告有效。

### 连带的第二个坑：渲染文字的临时层要比目标画布大一圈

字形高度正好等于画布高度时，画在**同尺寸**的临时层上会被裁掉一截，
量出来还是偏小。这个现象和"字号算错了"长得一模一样，很容易误判成
`fit_font` 有问题（实战里为此查了半天）。

**临时层四周各留出一倍字号的余量**，量完再裁。

### 字重也要对，而且要量

参考图是粗体、自己用常规体，笔画细一圈，看惯的人一眼就看出"风格不对"。
可变字体用 `set_variation_by_name()` 选变体：

```python
f.set_variation_by_name('Bold')
```

⚠ **变体也要量，别凭名字选**。实测同一字号下 `8` 的宽度：
`Bold` 是 35、`Bold SemiCondensed` 只有 30，而参考图是 38 ——
名字里有 Bold 不代表宽度对得上。

## 2. 量参考图：用连通域，不要目测

目测出来的尺寸误差足够让整页排版看着"哪里不对但说不上来"。
用连通域分析把每个元素的包围盒量出来：

```python
from scipy import ndimage
lab, n = ndimage.label(mask)                 # mask = 二值化后的前景
for sl in ndimage.find_objects(lab):
    h = sl[0].stop - sl[0].start
    w = sl[1].stop - sl[1].start
```

实战里就是这么拿到"大数字墨迹 38×56、徽标 50×25、进度条 50×8、
天气图标 49×41"这组数的，然后直接喂给上面的 `fit_font`。

## 3. 实拍照片要先做透视校正

手持拍屏幕一定带透视，四条边长不相等（实战里量到 234.3 / 230.6 / 232.2 / 234.4）。
**不要用最小外接矩形**，它只能纠正旋转，纠不了透视。

正确做法：

1. 二值化取屏幕暗区，**填掉内部文字形成的洞**（否则边界被文字打断）
2. **四条边各自做最小二乘拟合直线** —— 两端各掐掉 22% 避开圆角
3. 四条直线两两相交得到四个角点
4. 解透视变换矩阵，warp 到正方形

先校正再量尺寸，否则上一节量出来的数全是斜的。

## 4. ⚠ 取底色：别用"整屏中位数"

**这条不止适用于照片，从截图或设计稿取色是同一个陷阱**：
画面上的亮元素（发光的文字、图标、高光）会把整屏统计量抬高，
取出来的底色偏亮。

实战里第一次取到 `#031240`（偏亮），只量空白区域才得到真实的
`#01092F`~`#010A34` —— 两者肉眼可辨，用户一眼看出"太亮了"。

**正确做法：先框出确实没有内容的区域，只在那里取。**

### 照片另有一层：明度饱和度不可信

发光屏拍出来的照片，**明度和饱和度都被相机的曝光/白平衡改过**：

- **只有色相可以直接用**
- 明度、饱和度要按设计意图重新定，不要照吸

## 5. 改图集尺寸，必须同步改控件 rect

这条踩了三次，因为**它不报错**，只是静默重叠或被裁：

| 改了什么 | 忘了改 rect 的后果 |
|---|---|
| 数字图 11→12 宽、"月"字图 16→18 宽 | 日期渲染成 `12月1` + `5日` **重叠** |
| CITY 图做成 48 宽 | rect 还是 44，**右边裁掉 4px** |
| LB_HIGH 图做成 80 宽 | rect 还是 78，裁掉 2px |

`check_project.py` 查两层，改完图一定要跑：

- **图片 vs rect**：图比 rect 大就报（框架不缩放）
- **Time/Number 的内容总宽 vs rect**：按 `format` 展开算
  「数字图宽 × 字段位数 + 各分隔符图宽」

宽度怎么算有源码可依（`ui_platform.c` 的 `get_strpic_width()`）：

```c
for (i = 0; i < str_num; i++) {
    open_string_pic2(dc->prj, &file, *p);
    width += file.width;      /* 逐张图宽度直接累加 */
    max_h  = MAX(file.height, max_h);
}
```

**没有字间距，也没有 kerning** —— 总宽就是用到的每张图宽度之和，
总高是各图高度的最大值。所以只要 10 张数字图等宽（惯例如此），
静态算出来就是**精确值**，`check_project.py` 会报 ERROR；
数字图不等宽、或 `format` 里有不带宽度的 `%d`（位数要运行时才知道，
只能按 u16 上界 5 位估）时，只能给上界，降级成 note。

```
CLOCK_TIME_YMD  fmt='M-D'  内容 66  rect 66   ← 差 0px，再动就溢出
CLOCK_TIME_HMS  fmt='h'    内容 76  rect 76
```

顺带，这个检查还会报出另一类问题：**`format` 里的分隔符比 `delimiter` 列表多**
（Time 会从用完那里截断，后面字段根本不显示）。
样例工程 `BT_Watch` 页 4 的 `Y/M/D h:m:s` 就是这种情况 —— 6 个分隔符位只配了 2 张图。

## 5.2 ⚠ 改图片目录名，要同步改 json 里的全部引用

给图片目录改名/合并（`pic_ui` + `pic_music` → `pic_tft_ui` 这种）时，
工程 json 里的路径**不会跟着变**。后果是整个工程的图全部失效，
而且**只在跑资源生成时才暴露**，编辑器里看着还是好的。

实战里撞见过一次：922 处引用指向已经不存在的目录，
`check_project.py` 报了 916 条「图片找不到」。**这个 note 不要当噪音略过**，
它是 ERROR 级别的问题只是没归到 ERROR。

```sh
python tools/check_project.py <工程.json> 2>&1 | grep -c "图片找不到"   # 应当是 0
```

改名之后的修法就是全文替换，然后用上面那条复查归零：

```python
s = io.open(PRJ, encoding='utf-8', newline='').read()
s = s.replace('config/旧目录/', 'config/新目录/')
io.open(PRJ, 'w', encoding='utf-8', newline='').write(s)   # newline='' 保持原样，见 project.md §0
```

⚠ **别用 git bash 的 `ls` 去确认目录在不在。** 实测 `ls config/pic_ui` 会列出
`config/pic_tft_ui` 的内容（路径匹配把你骗了），而 Python 的
`os.path.isdir('config/pic_ui')` 老老实实返回 `False`。
**验证目录/文件存在性用 `os.listdir()` 打 `repr`，别用 shell 的 ls。**

## 5.5 ⚠ 透明区的 RGB 也要检查，不只是 alpha

"透明没做对"有**两种**，机理不同，都只在真机上露馅：

| | 现象 | 成因 |
|---|---|---|
| **假透明** | alpha 全 255 | 把底色画进了图里（见 `platform.md` 第 4 节） |
| **透明区带色** | alpha 对，但全透明像素的 RGB 是白/图标色 | 生成图时给透明区填了颜色 |

第二种的典型来源是这个写法：

```python
im = Image.new('RGBA', size, color + (0,))   # ← 透明区的 RGB 被填成了 color
im.putalpha(mask)
```

`alpha=0` 的像素 RGB 仍然是 `color`。有些合成路径只看 RGB 不看 alpha，
真机上就显示成**一大块色底**（实战里 SD 卡图标变成一块白）。

**实测官方切图的透明区 RGB 全是 0**，照着做就对：透明区一律填黑。

`check_project.py` 两种都查。第二种**按比例判**（超过一半的透明像素 RGB 非黑才报）——
因为 LANCZOS 缩放会在边缘留下少量带色的透明像素，那是正常的
（实测一批图最高也才 10.5%），按"有就报"会刷出几十条噪音。

## 5.6 复用既有图标：放大换色，而不是重画

产品有既定的图形语言时，**沿用原图标比重画更对**（用户会一眼认出风格变了）。
原图往往是给点阵屏做的 1bit 小图，放大换色的流程：

1. **先判极性再取墨迹。** 原图是纯黑白，但**极性可能不统一** ——
   实战里多数是白底黑图，`SDMMC.bmp` / `pause_sec.bmp` 却是黑底白图。
   按整图平均亮度判断，别假设。
2. **墨迹转 alpha，再 LANCZOS 放大。** 不能用最近邻，会放大成锯齿块。
   放大带 alpha 的图要预乘（见 `platform.md` 第 4 节那段代码）。
3. **上色**：新颜色 + 上一步的 alpha。
4. 实心风格要转描边时：**原图减去腐蚀后的图**就是轮廓。
5. 一张图里画了多个图标（`pause_sec.bmp` 里既有 ▶ 又有 ‖）时，
   **按列裁出需要的那半**。
6. **缩小同样走这条路**，不只是放大。缩小前**先按墨迹包围盒裁掉白边**，
   否则原图的空白边距会跟着缩、图标在控件框里偏小偏位
   （`linein.bmp` 标称 80x32，墨迹只有 80x23）。
7. 要在原图标基础上**添笔画**（补一段线缆、加一道斜杠）时，
   新笔画用超采样画再缩回目标尺寸，这样它的抗锯齿边缘才和
   LANCZOS 缩出来的原图线条粗细一致；直接在目标尺寸上画会明显更硬更粗。

> ⚠ 这一节是"按需求默认该走的路"，不是可选项。用户说"做个 xx 图标"时，
> **先去 `config/pic_lcd/` 找有没有现成的同义图标**，有就按上面加工；
> 直接新画一个形状，哪怕画得不难看，也会和产品既有图形语言对不上。

## 6. 排版自检：从 json 渲染整页，别手敲坐标画效果图

```sh
python tools/render_page.py <工程.json> <页号> -o out.png
python tools/render_page.py <工程.json> 3 -o out.png        --sample CLOCK_TIME_HMS=15 --sample CLOCK_WEEK_PIC=5 --sample CLOCK_TEMP_BAR=48
```

它复刻了设备端的几条绘制规则，所以能**同时**照出配色错、坐标错、裁切和遮挡。
关键是**背景填充判定**（`(color & 0xFFFFFF) != 0xFFFFFF` 才填）——
手敲坐标画的效果图几乎不会实现这条，于是照不出
"某个控件的背景色把整屏刷白"这类问题：坐标明明都对，画面却全白。

`--sample` 指定某个控件显示什么（Time/Number 给串、ImageList/Battery 给第几张、
slider 给百分比）；不给就按 `format` 自动填典型值。

⚠ **它是排版自检工具，不是模拟器**：Text 的文字画不了（只用紫色虚框占位）、
不画 `highlight_image`、不做列表滚动和高亮、`play_mode` 只画第 0 帧。
这几样"没画出来"是正常的。完整清单在脚本抬头。

> 和棋盘格 contact sheet 的分工：**contact sheet 查单张图**（假透明、边缘黑边），
> **render_page 查整页**（位置、遮挡、配色、裁切）。两个都要跑。

## 7. 交付前：素材别被 .gitignore 挡掉

工程的 `config/.gitignore` 里通常有一条 `*.png`，靠白名单逐个放行子目录：

```gitignore
*.png
!ctrl/*
!ctrl_pic/*
!ini/*
!pic_clock/*        ← 新建的素材目录必须自己加一行
```

**新建素材目录后忘了加白名单**，那一整批图都进不了版本库。
后果特别隐蔽：仓库里只剩编译好的 `JL.res` 二进制，
**别人 checkout 下来能烧录、但改不了界面**，而且短期内完全看不出问题。

提交前确认一次：

```sh
git status --porcelain <素材目录>          # 应该看到新增的图
git check-ignore -v <素材目录>/xxx.png     # 应该没有输出
git ls-files <素材目录> | wc -l            # 应该等于目录里的文件数
```
